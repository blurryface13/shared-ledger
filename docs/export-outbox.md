# 导出 Outbox：可靠发布第一阶段

## 行为

创建导出任务与 export_outbox 行在同一数据库事务提交。ExportOutbox.enqueue 强制要求已有事务，替换原 afterCommit 直接发送。记录唯一键为导出任务 ID。Relay 每秒领取一条到期记录，以 FOR UPDATE SKIP LOCKED 支持多个实例；等待发布确认最多 5 秒，事务超时配置 10 秒。消息持久化、mandatory 路由检查、correlated confirm 同时启用。

成功确认且未返回才标记 SENT。失败按 2^attempt 秒退避，上限 300 秒，8 次后 DEAD，不静默删除。仅记录异常类型，避免原始响应/凭据进入表。发出消息后数据库回滚会再次发送，因此是至少一次；现有消费者依靠导出记录 FOR UPDATE 与 SUCCESS 判断避免重复生成成功结果。

当前每次扫描一个任务、持锁等待确认是有意选择的简单实现，吞吐有限，不能描述为高吞吐发布器。代理/连接建立也可能影响实际耗时，5 秒是 confirm 等待限制而非全链路硬截止。需要压测后才考虑批量领取与租约。

## 数据库与运维

已有环境先应用 sql/docker/mysql/migrate/20260920_export_outbox.sql；新环境使用 005-export-outbox.sql。2026-09-20 后续验收已完成本地数据库备份、迁移及服务重启；不代表生产部署。

DEAD 为发布失败记录，尚无管理接口或告警；处理原因后可由运维在事务中确认当前状态，将该行重置 PENDING、attempts=0、next_attempt_at=当前时间进行重投。禁止直接删记录来“修复”。SENT 不表示消费已完成，应结合 tb_export_record 查看。此次不包含消费死信队列、历史 PENDING 任务回填、自动过期清理和端到端监控；上线前需要继续补齐。

配置 app.export.outbox.enabled=false 可停止扫描；事务仍写入待发送记录，恢复扫描后继续处理。测试 profile 默认关闭调度，以免异步处理干扰断言。

## 受控人工重试（2026-09-20）

`POST /api/v1/books/{bookId}/exports/{exportRecordId}/retry`，使用现有 Bearer 身份认证。

- 仅当前有效成员且为原导出发起者可操作；全账本汇总还重新检查账本所有者权限和账本有效性。
- 先锁导出记录，再锁 Outbox；只重置 DEAD，或业务 FAILED 且消息 SENT 的记录。旧版无 Outbox 的 FAILED 任务可补入队列。
- 重置与权限校验在同一事务中，重用原任务 ID，恢复为 PENDING、attempts=0；正在等待的发布不受重复点击影响，SUCCESS 快照不变。
- 消费失败重试排队期间业务状态仍是 FAILED，消费启动后更新；HTTP 成功只说明请求已处理，不表示导出成功。正常 PENDING/RUNNING/SUCCESS 请求是无副作用操作。
- 重试会读取执行时的账本数据；它不是对最初请求时刻的数据库快照恢复。

新接口记录 exportId/memberId 的重试日志，不记录正文或凭据。它不是完整持久审计系统，也没有告警面板或重试按钮。DEAD 的数据库维护方式保留为运维兜底；优先使用受权限控制的接口。

新增 3 项真实集成测试覆盖 DEAD、FAILED/SENT、旧失败任务、重复操作和权限拒绝，完整后端 64 项通过，见 [恢复回归报告](export-retry-regression.json)。仍需补充真实宕机、跨实例并发重试、DEAD 告警及消费死信治理。

## 导出列表发布状态

`GET /api/v1/books/{bookId}/exports` 在原发起者可见范围内新增：

- `deliveryStatus`：PENDING / SENT / DEAD；无 Outbox 历史记录为 LEGACY，不假设其已成功发送。
- `publishAttempts`：当前发布周期次数；LEGACY 为 null。人工恢复会重置，因此不是累计重试审计。
- `nextPublishAttemptAt`：仅 PENDING 提供；表示最早可再次扫描时间，不是保证完成时间。
- `retryable`：结合当前成员、账本有效性、汇总所有者、业务状态与发布状态计算。只是列表时刻提示，重试接口仍重新鉴权。

业务 FAILED + 发布 PENDING 表示恢复已排队，应等待而非再次手动提交。SENT 仅表示 broker 接收且可路由，不等于生成成功。已有创建导出接口的这些新增字段尚未提供实时投递状态，应以随后查询列表为准。

Outbox 仅查询已授权任务 ID，每批最多 200 条，避免逐条查询。当前导出列表本身尚未分页，批量读取并不解决无限历史列表的内存与响应大小问题。

回归覆盖状态变化、可重试标记、成员隔离、历史记录与成功结果保护；完整 65 项通过。此轮仅实现接口可见性，前端展示、告警、持久审计仍待接入。

消费端现有自动重试不能替代死信治理：当前队列声明未配置死信交换机。本轮没有变更现存队列参数，避免 RabbitMQ 同名队列属性不一致导致启动失败；后续应明确新队列迁移或策略部署，再测试重试耗尽、坏消息及恢复。

后续 E10 已使用应用层确认转存补充消费失败保留，保持原队列声明参数不变。详见 [失败消息保留与恢复](export-failure-retention.md)；上文无死信配置的描述为 E09 时状态，当前仍不使用 broker DLX。
