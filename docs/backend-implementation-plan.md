# 后端实施与验证计划

## 定位与技术决策

目标：传统 Java 后端岗位作品，能围绕真实业务回答“场景、方案、证据、代价、线上故障与恢复”。保持 DDD 模块化单体，沿用项目既有 Java / Spring Boot / MyBatis-Plus / MySQL / Redis / RabbitMQ，不因参考项目引入第二套 ORM、数据库、消息中间件、认证体系或微服务架构。具体依赖版本以本仓库 pom 为准。

复用排序：技术栈及领域边界适配 > 真实实现与测试质量 > 授权条件和维护情况 > 功能接近程度 > Stars。授权条件是复制代码的前提，不以栈相近为由忽略。现有账本模块是第一复用来源；TripFlow 只取独立协议、测试场景与可拆出的逻辑，不迁移 JPA/PostgreSQL/Kafka；TripStar 仅作高德与任务职责参考，GPL 代码不直接纳入；轻量 MIT 示例按需抽取工具调用骨架，不导入整套 Agent 平台。

## Agent 最小职责

路由是意图分类，不是地图道路寻路。先用显式操作与简单规则判断：新建规划、调整规划、查询已有规划、信息不足需要补充。自然语言模糊时才调用模型，输出有界枚举与经过校验的参数，不允许模型指定任意接口、SQL、URL 或工具名称。

流程：用户输入 → 身份与配额校验 → 意图/参数识别 → 受控 POI/路线查询 → 结构化 PlanDraft → Java 规则校验 → 用户预览 → 版本校验并采纳。

草案包含目的地、日期、人数、预算、偏好、按天活动、POI 引用与未解决问题。模型不生成权威道路几何、不直接写数据库、不执行结算。时间冲突、金额、成员权限、锁定活动保护、行程版本检查均由 Java 执行。缺少 API Key 或供应商故障时返回明确不可用状态，保留手动编辑；不静默用假数据冒充真实规划。

第一阶段不引入多 Agent、向量库、RAG、小红书抓取、自主循环或动态 MCP 插件。外部查询先实现普通 Java 适配器，后续需要时再包装为模型工具。

## 按场景设计与验证

以下为待实现/核验方案，不代表当前代码已具备，也不是已取得的性能结果。

| 场景 | 怎么做 | 如何证明效果 | 线上问题与处理 |
|---|---|---|---|
| 同行者重复点记账、网络重试 | 请求幂等键绑定操作者、账本与请求摘要；数据库唯一约束兜底；事务写账单和分摊 | 相同请求并发重放，只产生一笔账单且金额一致；不同内容复用键应冲突 | 请求成功但响应丢失：重试返回已存结果；幂等记录清理须有业务保留策略 |
| 多人同时改行程或绑定账本 | 聚合版本条件更新；唯一约束保护绑定关系；检查双方权限 | 两个同版本更新只有一个成功，另一个返回冲突；不丢失修改 | Agent 生成期间人工改动：草案携带基准版本，拒绝覆盖最新数据 |
| 多人同时确认收付款 | 数据库事务、状态条件更新、收付款记录唯一性；必要时固定加锁顺序 | 重复确认不重复抵扣；结算前后余额守恒；失败事务无半成品 | 死锁/锁等待：短事务、索引、锁顺序；仅对可重试错误做有限重试，不在事务中调用外部服务 |
| 热门行程/地点反复读取 | 先优化查询与索引，再引入读缓存；用户私有数据带权限边界；公共 POI 缓存按供应商许可 | 比较无缓存/有缓存 P95、数据库查询数、命中率；检查越权与脏读窗口 | 热点失效：TTL 抖动、请求合并、有界并发；事务提交后失效，失败重试；不宣称缓存强一致 |
| 外部地图慢、限流或超时 | 连接/请求超时、并发隔离、限流、仅对适合错误退避重试；按段保存来源和状态 | 注入超时/429/坏响应，检查总时限、调用次数及线程占用 | 一段失败不伪造零距离；可展示仍有效的旧数据及时间，超出许可或有效期则不可用 |
| 规划/导出请求积压 | MySQL 持久化任务；事务 outbox；RabbitMQ 确认、幂等消费、重试与死信；有界 worker | 任务排队时长、完成率、重投次数；重启后任务不丢，结果不重复落库 | DB 提交后发送失败由 outbox 补发；消费成功 ACK 丢失靠幂等；消费者中断靠租约/超时回收 |
| 上传凭据/照片和导出 | 对象存储直传策略与服务端确认；大小、类型、像素限制；短期签名访问；异步处理 | 大文件不压垮应用堆；跨账本访问被拒；导出不夹带私密凭据 | 上传完成但业务关联失败：清理孤儿对象；恶意文件/解码超限：拒绝和隔离；存储供应商待确定 |
| 数据量增长下账单列表/统计 | 按实际过滤排序设计联合索引；游标或受限分页；先查执行计划再决定汇总表 | EXPLAIN、慢查询、扫描行数；代表性数据量下的延迟曲线 | 深分页、N+1、锁竞争优先从 SQL 排查；不提前分库分表 |

Redis 分布式锁只在明确存在跨实例互斥且数据库约束不足时采用，并说明租约、续期、持有者校验和 fencing；账单正确性不只依赖锁。RabbitMQ 首先服务真正耗时且可重试的任务，不为每次 CRUD 发消息。

## 性能结果的证据要求

分别测试普通业务接口和外部依赖任务，不能把 LLM 的几十秒等待掩盖在一个平均响应时间里。

- 基线记录：提交 SHA、JDK/JVM 参数、CPU/内存、数据库版本与数据量、索引、连接池、缓存冷热、部署拓扑。
- 请求模型：接口比例、读写比例、并发或到达率、热点比例、身份分布、持续时间；逐档增加压力，观察饱和点。开放到达率可暴露排队，避免仅用封闭并发误判吞吐。
- 指标：吞吐、P50/P95/P99、超时/错误率、线程与连接池等待、CPU/GC、SQL 扫描、缓存命中、队列深度/最老消息年龄、供应商调用量。
- 正确性优先：重复账单数必须为零，余额守恒、权限隔离、任务结果唯一性必须通过；错误响应不计为成功吞吐。
- 对照实验：只改变一个因素，至少重复运行并报告波动；区分本地模拟供应商与真实供应商测试，不向第三方执行压力测试。
- 故障演练：外部服务延迟/限流，消费者重启、重复投递、缓存不可用、数据库锁竞争。记录恢复时间、是否丢任务、是否重复记账。

当前没有压测数据，不写“支持万级并发”“性能提升 80%”等结论。性能目标在运行环境、代表性数据和第一次基线结果确定后设定。小型结伴旅行应用通常并发不高，面试中说明压测是容量与正确性验证，不声称已有真实高流量用户。

## 实施次序与完成标准

### P0：现有后端盘点与可运行基线

梳理现有未提交修改、已有功能/测试、配置和迁移脚本；本地启动原服务，验证原账单/审批/结算流程，确认技术版本和领域依赖。保留用户未提交内容。输出能力缺口表，不重复实现已有服务。

### P1：Trip 核心与前端第一条真实链路

新建/读取/修改/归档/恢复 Trip，TripDay/Activity 顺序、日期校验与版本；可选账本关联及权限。数据库迁移和业务测试，前端切换成真实接口，刷新/重启后可读。账本成员与行程参与者不隐式合并。

### P2：POI 与真实路线

供应商端口和高德适配器，地点消歧、坐标系、真实 polyline/距离/时长、缓存与超时。未确定餐厅/酒店不编造坐标。前端用真实几何替换示意图，不申请定位权限。

### P3：轻量规划

意图识别 → 后端任务 → 结构化草案 → 规则校验 → 预览与采纳。提供任务持久化、幂等、版本冲突和故障恢复，不扩展成 Agent 平台。

### P4：上线准备与面试证据

检查现有账本业务并发正确性；基线压测、针对性优化与对照；指标、日志 traceId、敏感数据脱敏、配置/密钥隔离、备份恢复与部署回滚。导出、媒体、水印按真实代码准备情况补齐，算法未提供前只定义任务接口。

每个阶段交付：代码 + 数据迁移 + 必要测试 + 实际测试结果 + 简短 ADR。复用代码保留来源与适用许可证；简历上明确哪些是本人设计/优化，哪些基于开源适配。

## 面试讲解模板

业务场景与规模假设 → 原实现和瓶颈证据 → 考虑的备选及取舍 → 关键实现 → 同环境对照数据 → 失败场景与恢复 → 当前限制。

例如：结算确认在并发重试下可能重复抵扣，用状态条件更新和唯一约束保证一次生效；并发重复提交验证记录唯一与金额守恒；再测锁等待与事务时长。没有实测前不填性能数字。
