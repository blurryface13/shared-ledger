# 导出消费失败消息保留

## 行为与部署

消费自动重试耗尽后，ExportFailureRecoverer 将原消息发布到 `${exportExchange}.failed`，路由键 `failed`，持久队列 `${exportQueue}.failed`。保留原 body/messageId，额外添加异常类型和原队列名，不添加异常正文或堆栈。消息与拓扑均为持久配置，发布检查 correlated confirm 和 mandatory return。

只有确认成功才正常返回，从而允许原消息确认；失败或确认超时抛出 ImmediateRequeueAmqpException 保留原消息。确认等待 5 秒不是网络全链路截止。发送成功但确认丢失可能再次发布，失败队列允许重复证据，不能假设一条任务只留一份消息。

这是应用层失败转存，不是给旧队列追加 broker DLX 参数。旧业务队列声明保持不变，避免同名队列参数冲突。派生名称跟随测试消息命名空间，测试不会写业务失败队列。未来增加其他消费者时，需要按消费者明确配置 recoverer，不能直接把目前导出专用恢复器泛化到所有业务。

## 恢复操作

1. 检查业务状态、Outbox 状态及失败队列积压。SENT 只说明原消息已发布，不代表消费完成。
2. 用 messageId 或 body 中 exportRecordId 定位任务，核对权限及失败原因；失败队列访问应仅向运维开放。
3. 修复原因后，由仍有权限的原发起者调用 `POST /api/v1/books/{bookId}/exports/{exportRecordId}/retry`，然后查询任务，确认 SUCCESS 和快照内容。
4. 对已确认处理的保留消息逐条确认/归档。禁止清空整个失败队列；不存在的任务 ID 或无效消息不能盲目重新发布，应单独排查。

目前保留队列没有自动消费者，不会自动循环重放。没有提供批量清理工具。缺少持续告警、保留期限、持久化人工处理审计，队列可能不断积压。

## 验证与边界

完整后端 67 项通过，见 [回归报告](export-failure-retention-regression.json)。真实监听器收到不存在的任务 ID，自动重试耗尽后消息到达独立失败队列；另验证无法路由时恢复器抛出重新入队信号，以及消息正文、messageId、持久属性和脱敏异常类型保留。

该测试没有证明 broker 整体宕机时的恢复时间，也未注入“转存确认完成但原消息确认前进程退出”。失败队列不可用时会反复执行重试周期，需要监控、背压与人工暂停策略；现有每周期退避不能称为全局熔断。无效 JSON、反序列化前失败等毒消息路径仍需专项测试。单节点持久化也不等同于集群高可用。

本轮不新增数据库表。状态告警可围绕失败队列非空、Outbox DEAD、最老 PENDING 年龄、业务 FAILED 数量建立，但尚未部署这些告警。
