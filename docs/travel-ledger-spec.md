# Shared Ledger · 旅行共享账本规格

版本：0.1 · 2026-09-19 · 状态：产品方向已确认，分阶段实施。

## 1. 目标与取舍

以现有 Java 21 / Spring Boot 4.0.3 / MyBatis-Plus / MySQL 工程为基础，坚持 DDD 模块化单体。产品服务结伴短途旅行：规划、协同调整、记账、结算、相册与分享。传统 Java 后端工程和学习是主线，旅行 Agent 是可关闭的增强功能。

- 第一阶段：国内单城市、1–3 天、单币种 CNY、小团队；普通共享账本独立可用。
- 不申请定位，不采集实时/后台轨迹，不自动判断到达。路线起点取住宿或手动选择地点，打卡由用户主动完成。
- 路线预览是计划的可视化，不能表述为真实移动轨迹。
- 不开发预订支付平台，不接管携程账户，不假设能调用携程订单 API。
- 水印算法由用户后续提供，本阶段仅定义端口、状态和 UI，不能用可见文字水印冒充算法。
- 当前设计原型与生产小程序分开，验证后将组件与交互迁入 uni-app；不以原型演示结果代表真实服务成功。

## 2. 已有基础与待核验边界

现有包包含 identity、ledger、billing、settlement、export、shared；具有微信登录、账本成员/邀请、账单、结算、文件上传入口。已有 Redis 和 RabbitMQ 代码。工程笔记注明导出仍有 snapshot 占位结果、前端轮询未完整接入等边界，不能直接宣称生产就绪。

文件上传当前会压缩图片；接水印前必须梳理压缩顺序与原件保留策略。先对现有功能做基线回归，保留有效领域规则，不重写成熟能力。不做未经验证的大范围删除。

仓库： https://github.com/blurryface13/shared-ledger 。按文档、前端、领域功能分别提交；只提交本次明确变更，不包含环境变量、凭据、上传图片和本地构建文件。

## 3. 核心用户流程

1. 创建旅行：目的地、日期、人数、预算（必须注明总预算/人均）、交通方式、住宿位置或偏好、文化/经典/自然等偏好、紧凑/适中/轻松节奏。
2. 手动建行程或请小炫汤圆生成草案。日期和地点明确后可使用默认偏好，默认值可见可改。
3. 每天展示活动卡、交通连接、空闲时段；支持新增、编辑、排序、删除、锁定活动。展示预计停留和交通时长。
4. 修改后预览变化与冲突，确认新版本；已完成、已锁定和已确认订单不被 Agent 隐式覆盖。
5. 活动可关联记账：带入名称、类别、日期、地点，明确付款人、实际金额及分摊成员。规划预算不自动生成实际账单。
6. 主动完成活动、添加照片和笔记；凭据只在账本授权范围查看，相册分享需显式选择。
7. 旅行结束查看支出、差额与结算，导出行程或账单；相册生成独立分享版本。

验收示例：4 人杭州两日游，锁定酒店订单；删除下午景点后仅重排剩余未锁定活动；新增午餐 186 元由甲支付、四人均分，支出增加 186 元且无重复账单；结算转账不再次计入消费。

## 4. 视觉与交互约定

最新参考图优先：安静的浅色底、炭灰文字、雾蓝/鼠尾草/灰粉活动卡、明显的时间与地点层级、独立交通行、斜线纹理空闲段。早期咖啡记录图作为温暖生活感的补充。屏幕中的社交平台 UI、作者品牌和宣传文案不复用。

物理场景：旅行者在白天的酒店或街边单手查看今天安排，需要快速读清时间与下一站，因此采用浅色、高对比正文、大触控目标。

- 行程：每日切换、住宿基点、时间卡、交通连接、添加活动；地点详情可展开，保留笔记、编辑、记账操作。
- 账本：沿用日期节奏、低饱和类别块、金额明确；预计预算、实际支出、待结算金额各有准确标签。
- 水印：以相册/照片为主，处理状态次之；未接服务时明确“待接入”，不提供假成功。
- 导出：斜放纸张与背后叠页形成预览，纸面本身用真实行程数据；点击进入正视阅读。打印/导出时取消倾斜、阴影和界面控件，保证分页与文字清晰。
- 小炫汤圆：Agent 头像和规划状态形象，正式素材待用户提供；草图头像明确为临时素材。
- 动效用于卡片展开、页面状态和主动路线播放，支持 reduced-motion；不依赖动画才能理解信息。
- 手机优先，大屏可显示行程与导出预览双栏。按钮至少 44px，键盘焦点清楚，颜色不是唯一状态提示。
- 原型无需定位权限。示意路线标注“示意”；接真实数据后才显示导航路线和服务来源。

## 5. DDD 限界上下文与职责

| 上下文 | 聚合与职责 | 边界 |
| --- | --- | --- |
| identity | User、会话、身份 | 复用现有登录；令牌不跨模块散落处理 |
| ledger | Book、Membership、Invitation | 账本访问控制、角色、邀请有效期 |
| journey（新增） | Trip、DayPlan、Activity、BookingImport | Trip 管旅行元信息；DayPlan 管一天活动与版本，避免巨型聚合 |
| billing | Bill、Split、Money | 支付人、分摊、精度、账单生命周期 |
| settlement | Settlement | 已确认账单快照、结算差额与确认；单币种净额总和为零 |
| planning（新增） | PlanningJob、Proposal | Agent/规则编排产生提案，通过 journey 应用服务采纳 |
| media（演进） | MediaAsset、ProcessingJob | 原件、衍生版本、归属、可见范围、水印任务 |
| export | ExportJob、ExportSnapshot | 一致版本快照、文件生成、授权下载 |

依赖：interfaces → application → domain；infrastructure 实现 domain/application 定义的端口。领域模型不得依赖 Spring MVC、第三方地图响应或 LLM SDK；DTO 与持久化模型不直接充当聚合。跨上下文通过应用门面或领域事件协作，禁止互相调用 Mapper 写表。

值对象：Money（BigDecimal + currency）、TimeRange、PlaceRef（provider + poiId + coordinateSystem + coordinates）、TravelPreference。时间持久化保留时间点与时区，第一版 UI 仅国内时区。

精简原则：只有含业务规则的概念成为领域对象；简单查询使用读模型，不机械增加接口/实现/转换层。不先拆微服务、不为面试堆无业务依据的中间件。抽取重复鉴权/异常/校验，保留模块职责，重构必须有行为基线。

## 6. 领域不变量与一致性

- 同一天活动的起止时间合法；交通与休息时间纳入校验，跨天行程第一版明确拒绝或要求拆分。
- 活动更改使用 dayPlanVersion；冲突返回 409 和当前版本，用户重新合并，不能静默覆盖。
- 行程人数是规划输入，账本真实成员是权限与分摊依据，两者不能混用。
- 账单分摊之和等于总金额；以分为单位分配舍入余数，算法稳定且可解释。
- 新增账单与分摊在同一数据库事务内；扣除/冲销和结算有明确状态迁移与审计。
- Idempotency-Key + actor + operation 唯一约束，保存请求摘要和结果；同 key 不同请求返回冲突，成功重试返回相同结果。
- MySQL 为事实源；Redis 锁不能替代数据库版本/唯一约束，也不能假设租约不会过期。
- 事务 Outbox 与业务记录同事务提交；消息至少一次投递，消费者按业务键去重；重试、死信和人工补偿可观察。
- 导出绑定确认版本快照，期间编辑不改变正在导出的内容。

## 7. Java 技术栈与学习验收

沿用 Java 21、Spring Boot 4、Spring Security、MyBatis-Plus、MySQL；按真实需求使用 Redis、RabbitMQ、对象存储。数据库迁移选 Flyway；测试使用 JUnit 5，关键集成用 Testcontainers；上线使用 Docker、反向代理 HTTPS、CI 检查与 Actuator/Micrometer。新增依赖前核对与当前 Spring Boot 主版本兼容。

| 学习主题 | 项目落点 | 必须能解释/验证 |
| --- | --- | --- |
| Java 集合、泛型、equals/hashCode | 地点去重、稳定排序、值对象 | HashMap 键不可变、复杂度、排序稳定性 |
| BigDecimal、时间 API、异常 | 分摊、预算、行程时间 | 禁用浮点金额，舍入规则、业务异常与系统异常 |

| MySQL 索引、MVCC、锁 | 成员账单查询、版本冲突 | EXPLAIN、联合索引、隔离级别、死锁重试边界 |

| JVM 与性能分析 | 大图处理、导出、批量查询 | 堆/GC、内存峰值、线程与连接池、慢 SQL |
| 测试与发布 | CI、迁移、监控、回滚 | 集成测试、备份恢复、健康检查、故障定位 |

## 8. 小炫汤圆规划 Agent

输入：目的地、日期、人数、预算口径、风格偏好、节奏、交通方式、住宿偏好/已订酒店、必须去/不想去、锁定订单和已有行程版本。

采用单 Agent + 有界工具循环；不引入多 Agent 群。Java 承担编排与领域校验，LLM Provider 经端口接入。无模型或超时可退回规则草案/手动编辑。

工具白名单：searchPlaces、getPlaceDetails、estimateRoutes、checkTimeWindows、readConfirmedBookings、validateProposal。工具服务端注入用户/旅行权限，不信任模型传来的身份参数。模型不能执行 SQL、任意 URL、支付、删除账单或直接发布行程。

流程：
1. 结构化偏好，缺关键条件时只追问必要信息。
2. 查询候选地点并记录 provider、poiId、来源时间；网页/订单文本按不可信数据处理。
3. 根据可用工具结果构思候选安排，Java 计算交通、时间窗口、预算约束。
4. 有界修订最多 2 次；工具调用最多 12 次、任务最长 60 秒作为初始可配置限额，压测后调整。
5. 返回结构化 Proposal：activities、routeLegs、estimatedCost、warnings、sources、changeSet、baseVersion。
6. 用户预览变化后采纳，journey 应用服务再次校验权限、版本和不变量。

成本/质量指标：有效地点比例、时间冲突数、锁定项目保留率、修改范围准确性、规划耗时、工具失败率、每次成本与用户采纳率。用固定场景集比较规则规划与 Agent，未改善则保持规则方案。

地点搜索不保证有营业时间/门票/消费价格；缺失字段显示“待确认”，估价注明估算，不生成伪实时数据。路线绘制仅用地图服务返回的有效坐标，统一坐标系与单位。

## 9. 订单导入

第一步支持手动录入交通/住宿订单；下一步允许用户粘贴订单文本或上传截图，经 OCR/解析后展示待确认字段，不自动落为已确认活动。

BookingImport 状态：UPLOADED → PARSED → NEEDS_REVIEW → CONFIRMED / REJECTED。字段含类型、起止地点、时间、时区、金额口径和原始来源。订单号脱敏，以来源摘要去重；截图按私密凭据管理。确认后写入锁定活动，可选择生成待确认账单，但不能自动把总价变成人均或重复记账。

本项目无携程账户集成权限，不能复用其内部库存和订单同步能力。

## 10. 媒体与水印端口

MediaAsset 保存归属、用途（gallery/receipt）、原件引用、摘要、衍生版本和可见范围。原件私有；相册分享只暴露选定衍生图，凭据默认不出现在公开导出里。

处理链：上传校验 → 安全存储原件 → 规范化尺寸/方向 → 算法嵌入 → 校验 → 发布分享版本。缩略图独立生成，提取应选明确的水印版本；算法嵌入后的再次压缩策略需实测确定。

WatermarkPort：submitEmbed(assetId, payloadRef, algorithmVersion, idempotencyKey)、submitExtract(assetId, algorithmVersion)、getResult(jobId)。提取输出 payload、confidence、定位结果及明确的成功/失败/无法判断状态；不信任任意置信度阈值。

算法服务后续可用 Python 隔离部署，Java 负责授权、任务、超时、重试、失败补偿。固定块尺寸、分割定位、最小图像尺寸、裁剪与缩放鲁棒性由用户算法代码和测试确定，不在本期实现。任务失败不阻塞原始记账。

## 12. 上线与验收门槛

- 权限：非成员不能读写旅行/凭据/导出，退出成员的后续访问失效；分享链接可撤销、有期限。
- 并发：两个客户端基于同一版本修改，只能一方成功；并行重试记账只能产生一笔。
- 正确性：分摊总和相等、结算净额和为零、重试不会重复消费、导出不混入未授权凭据。
- 故障：地图超时可手动继续；MQ 重投不重复发布；模型无效输出不会写入正式行程；算法关闭显示待接入。
- 上传：限制大小、像素总量、格式与解码资源；对象存储签名访问；过期临时资源清理。
- 运行：服务端保存第三方密钥、日志脱敏，记录 traceId；数据库迁移可追踪，备份恢复演练；CI 编译、关键测试、依赖检查后发布。
- 地图调用额度、缓存/存储授权、上线资质按选定服务正式规则核验，不承诺无限免费。
- 性能目标需注明硬件/数据量/并发，先测量再设置 SLA，不虚构高并发指标。

## 入口与可选关联补充

- 行程、账本分别拥有“新建 / 已有 / 历史”入口，用户无需先建旅行即可记账，也无需创建账本即可规划。
- 当前前端按可选一对一关系演示。绑定、改绑与解绑仅改变引用，不复制账单、不更改成员、不传播预算。Java 接入时用独立的关联应用服务校验双方权限和唯一关系，事务中更新，处理并发改绑。
- 历史先定义为手动归档，支持查看摘要与恢复。生产归档权限、已结算记录规则由各自聚合负责，禁止级联删除另一侧数据。
- 日期范围变化驱动行程天数、页签、导出和日期牌；账单保存自身消费日期，不随 Trip 改期移动。
- 前端多记录、关联与历史目前仅存本机，Java 的多聚合持久化和关联接口是后续实现项。


## 路线地图页（界面已实现，服务待接入）

入口为行程详情的“查看路线”，不占用第四个底部导航。桌面地图与地点列表并排，手机地图上方、地点下方。按天读取当前行程顺序，选中地点可回到对应行程卡。播放仅表达行程顺序，可暂停，遵循减少动态效果设置。

真实路线的数据链路：
1. 用户/Agent 确定活动后，由地点查询适配器解析供应商 POI ID、坐标、坐标系和来源。餐厅待定、酒店待定等不得编造坐标，需要选择具体地点。
2. Java 应用服务读取行程版本与交通方式，查询相邻 POI 的路线，返回每段 polyline、距离、预计时长及查询时间。供应商密钥由服务端保管；前端 SDK 的公开 key 按供应商要求做域名限制。
3. 前端只按返回坐标系绘制，不自行把顺序连线当道路。缺失地点、无可达路线、超时、配额失败分段显示，不替换成未经说明的直线距离。
4. 缓存键包含地点、方式、供应商与必要出行条件；缓存与展示遵循服务协议。任务绑定行程版本，异步旧结果不得覆盖用户最新修改。
5. Agent 只建议地点和顺序，不生成道路坐标；由领域校验比较交通时长与活动间隔，提示冲突后让用户调整。

计划的响应字段：tripId、day、itineraryVersion、mode、status、stops（activityId / poiId / coordinate / coordinateSystem / resolutionStatus）、legs（fromActivityId / toActivityId / geometry / meters / seconds / source / queriedAt / status）。接口路径与地图供应商在后端接入时确定。

该流程无需实时定位：起终点来自用户行程与选定 POI。当前原型仅实现顺序示意画布，未执行坐标查询和路线计算。
