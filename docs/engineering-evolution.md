## E00 · 从页面原型走到业务闭环

**当时状态。** 账本已有成员、邀请、临时参与人、审批、结算、凭据和导出等基础能力；新页面需要与这些后端能力对齐。旅行需要独立持久化，也允许关联账本。

**问题与动机。** 页面能展示样例，并不能证明刷新后存在数据、多人操作合法或金额计算正确。求职项目需要能解释业务约束如何落在 Java 和数据库里。

**采取方案。** 沿用 DDD 模块化单体，使用 MyBatis-Plus / MySQL 持久化；金额采用整数分并校验分摊守恒；旅行聚合通过版本更新控制冲突，后端承担所有权校验与规模限制。前端接入接口，支持按日编辑、移动与排序。接通高德地点与步行路线查询；规划先生成规则草案。

**效果与证据。** 基础接口和页面已联调，历史交接记录记载 39 项 Java 测试及当时 8 项前端测试通过。这是历史范围，不是当前分支的全量回归结论。参见[后端现状](backend-readiness.md)、[账本覆盖](ledger-ui-coverage.md)。

**剩余问题。** 真实微信身份、原生小程序迁移、生产部署未完成；图片仍使用本地存储。地图已有缓存和实例内并发限制，但尚不具备全局供应商配额治理。

**企业场景与学习。** 分层的价值在于让领域规则、事务边界、外部 API 各自可替换和验证。面试应能说明：金额为什么不用浮点数；多人修改如何发现冲突；数据库已写入但页面报错会怎样。

## E01 · 修复 Redis 标记所有权竞态

**当时状态。** Redis 幂等防护采用带 TTL 的占位，业务失败后删除标记。

**问题与动机。** 已复现的竞态：请求 A 执行太久，标记过期；B 获取新标记；A 随后失败并删除标记，误伤 B。仅知道 key 存在不能证明自己仍是持有者。

**采取方案与取舍。** 为请求保留 UUID 所有权令牌，用 Lua 原子比较令牌后再删除。清理失败作为 suppressed 异常保留，不能覆盖最初业务异常。保持现有技术栈，先修复正确性；不把引入锁框架等同于解决全部并发问题。

**效果与证据。** 修复前过期接力用例失败，修复后 5 项真实 Redis 测试通过，覆盖并发占位、失败重试、过期接力及清理异常；与 6 项旅行领域测试一起验证，共 11 项。提交 `7358ba1`。

**剩余问题。** TTL 去重无法永久防重，锁租期也不能替代数据库约束。账本锁的超时、续租或 fencing 仍需单独评估。

**企业场景与学习。** 慢请求、长 GC 或外部服务阻塞都可能让租期过期。面试重点：为什么 GET 后 DEL 两条命令不够；解锁为什么必须校验所有者；分布式锁保护与数据库最终正确性的关系。

## E02 · 将记账幂等落入 MySQL 事务

**当时状态。** Redis 防护已修复所有权，但请求超时后，客户端无法可靠知道是否已经记账；TTL 过后重试仍可能产生重复账单。

**问题与动机。** 这是设计风险，并非已有生产重复账单事故。目标是同一业务请求在重试时返回原结果，而不是简单提示「重复请求」。

**采取方案与取舍。** 以用户、账本、操作和请求键组成唯一范围；对规范化 JSON 计算 SHA-256 摘要，同键不同内容拒绝。通过唯一约束与行锁串行化竞争，把幂等记录、账单写入和响应快照置于同一个数据库事务；重放前仍检查当前权限。使用 JdbcTemplate 与 MyBatis 共用数据源和事务，不依赖进程内锁。暂保留缺少请求头的旧客户端 Redis 路径。

**效果与证据。** 9 项真实隔离 MySQL 测试覆盖新实例重放、事务回滚、6 个并发请求只产生一份业务效果、摘要冲突、范围隔离和序列化等；加上 Redis 5 项、旅行领域 6 项，共 20 项通过。随后迁移 004 已在本地应用。提交 `679d701`；设计见[持久化幂等](durable-idempotency.md)。

**剩余问题。** 无请求键旧客户端不具备同等保证；键的保留期限不能随意缩短，否则旧请求可能重新执行。数据库锁等待、连接池压力和事务超时仍需容量测试；配置事务超时不意味着完整 HTTP 链路硬超时。

**企业场景与学习。** 弱网重试、客户端重复点击、服务实例重启。重点解释唯一约束、事务传播、行锁及结果重放如何配合；不要将业务效果防重描述为网络请求只发送一次。

## E03 · 用真实链路发现代理丢请求头

**当时状态。** 后端幂等测试通过，前端也生成了请求键，但浏览器操作后新增的持久幂等记录数量不符合预期。

**问题与动机。** 这是本地真实联调发现的问题。代理的请求头白名单没有转发 `Idempotency-Key`，使浏览器实际退回旧逻辑。仅测试后端或前端 API 包装均无法覆盖这一跳。

**采取方案。** 修复本地代理白名单，增加真实 HTTP 代理转发测试，核对请求头和请求体。重启代理后，通过浏览器再次提交并检查账单与幂等记录。

**效果与证据。** 测试账本 73 中，修复后浏览器提交的 4.56 元账单有对应持久幂等记录。该账本包含联调过程的 4 笔账单，不能把这些测试操作误判成同键重复写入。见[实际联调证据](idempotency-live-result.json)，提交 `ed74169`。

**剩余问题。** 此次并未覆盖真实浏览器的断网后重试。后续部署若加入网关、反向代理，需要保留同样的端到端检查。

**企业场景与学习。** 单层正确不等于整条链路正确。定位应追踪请求键是否到达服务、是否落库，而不仅观察页面成功提示；生产可用 traceId 关联链路，但避免记录敏感账单正文。

## E04 · 区分明确拒绝和结果未知

**当时状态。** 前端保留请求用于重试，但如果后端明确拒绝参数，也一直保留旧请求，就妨碍用户修正表单。

**问题与动机。** 两种状态需要不同处理：明确未被接受可以编辑；网络超时或其他不确定错误可能发生在提交之后，贸然生成新键可能重复记账。

**采取方案。** 统一提交入口；仅在约定的明确校验失败 `4001` 下清除待重试请求。网络错误及其他未证明未提交的状态保留原键和原请求体。对错误语义采用保守处理，不把所有失败都视为可安全重新创建。

**效果与证据。** 前端累计 17 项测试和 1 项代理测试通过。通过代理对账本 74 验证：错误分摊无账单，同键修正后成功，再次重放仍一笔，更改内容被拒。见[共享账本联调证据](shared-idempotency-live-result.json)，提交 `77d61b1`。

**剩余问题。** 此验收为单成员共享账本，不代表完整多人审批与结算通过。错误码「明确未提交」的含义需要后端持续保证。

**企业场景与学习。** API 错误分类会影响资金类业务正确性；用户看到失败，不代表事务回滚。前后端必须共享可重试与可修改的契约。

## E05 · 页面刷新后恢复待确认请求

**当时状态。** 待重试请求只在内存中，刷新页面会丢失原键和请求体。

**问题与动机。** 服务已提交而响应丢失时，刷新后新建请求可能重复记账。需要在发送前保存恢复材料。

**采取方案与取舍。** 按用户与账本隔离，将原键和请求快照先写入 sessionStorage，再发请求；恢复时校验操作白名单与账本路径，禁止新请求覆盖待确认请求。页面显示待确认金额并提供原请求重试。成功或明确校验拒绝后清理；存储失败则在发送前停止。

**效果与证据。** 新增 6 项测试，前端累计 23 项与 1 项代理测试通过，覆盖重新创建 API 实例后的恢复、隔离、存储异常、覆盖阻止与篡改路径。提交 `10a41f9`。

**剩余问题。** 只覆盖同一标签页刷新，不保证关闭标签页、跨设备或离线长期恢复。尚未进行真实浏览器断网—刷新—重试演练；凭据上传的部分成功也需单独处理。

**企业场景与学习。** 正确性是客户端状态机与服务端事务共同形成的。先存再发的顺序、恢复信息的隔离和清理条件，都应进入回归用例。

## E06 · 导出任务引入事务 Outbox

**当时状态。** 导出任务创建与 RabbitMQ 消息发送存在提交后空隙。若数据库提交后、消息发送前进程退出，任务可能一直等待。

**问题与动机。** 这是故障窗口分析，不是已发生的线上丢单。目标是让「需要发送消息」本身具有持久记录，同时处理 RabbitMQ 不可用与消息无法路由。

**采取方案与取舍。** 在创建导出任务的同一事务写 Outbox；独立扫描器使用 `FOR UPDATE SKIP LOCKED` 领取待发送记录，等待 publisher confirm，检查 mandatory return，成功后置为 SENT。失败指数退避，最多 8 次后 DEAD。消息持久化，保留业务标识；消费者沿用行锁和成功状态防止重复业务效果。选择至少一次投递，允许确认后数据库回滚导致重投。

当前实现每次扫描处理一条、默认间隔 1 秒，发布确认期间持有数据库事务；实现直观，但吞吐与连接占用有代价。未来只有在测量证明瓶颈时，再设计租约领取、批处理与并发工作器。

**效果与证据。** 新增 6 项真实 MySQL 测试与 2 项真实 RabbitMQ 测试，覆盖事务回滚、扫描器重建、退避、DEAD、并发跳过锁行、发布后回滚导致重发，以及成功路由和无法路由。加上已有 20 项，共 28 项指定范围通过。提交 `8506a8d`；详见[Outbox 设计](export-outbox.md)。

**剩余问题。** 迁移 005 尚未应用到运行服务，尚未重启联调；历史等待任务补偿、DEAD 管理入口、DLQ、告警、清理策略及真实进程终止演练未完成。该轮未重跑完整账本集成回归。确认等待 5 秒不是端到端超时保证。

**企业场景与学习。** 数据库和消息代理是两个提交边界。Outbox 解决发送意图不丢，消费幂等处理重复；DEAD 可见不等于有人处理。下一步需要把技术机制延伸到可观测、告警与人工恢复。

## E07 · 让回归测试与实际部署跟上 Outbox

**当时状态。** E06 的专项测试通过，但旧业务集成测试依赖自动发布，而测试 profile 已关闭 Outbox 扫描；运行服务也仍是旧版本。

**问题与动机。** 代码检查发现测试只等待导出快照，并未触发 relay，会无法得到结果。这是检查发现的测试适配缺口，不伪称已经运行失败。同时，单独隔离数据库还不够：若测试和本地服务共享业务队列，本地消费者可能拿到测试任务 ID，在错误数据库处理。

**采取方案与取舍。** 测试显式创建真实 relay 并驱动一次发布，保留 RabbitMQ 与真实消费者处理；没有直接调用业务方法绕过消息边界。完整回归使用独立数据库、消息队列/交换机及 Redis 前缀，并把消息隔离补入统一回归脚本。测试调度保持关闭，使执行时机可控。

**效果与证据。** Java 21 构建镜像中完整 Maven 测试 61 项通过，失败/错误/跳过均为 0；见[分测试类报告](backend-regression-20260920.json)。前端 23 项与代理 1 项通过。运行库先备份，再应用增量迁移 005 并重启，健康检查通过。通过 4178 代理创建导出任务 12，PENDING → SUCCESS，Outbox SENT、发布 1 次；快照与原账本均为 4 笔，源数量未变，见[联调报告](outbox-live-result.json)。单次约 0.555 秒的观察不构成性能结论。

**运行与恢复。** 本地备份位于 `/tmp/trip-ledger-before-outbox-20260920.sql`，权限 0600，不提交仓库；这是临时备份，不是正式备份制度。扫描故障可用 `app.export.outbox.enabled=false` 停止 relay，保留待发送记录；本轮没有做恢复备份或旧版本回滚演练。隔离回归库及对应消息资源保留用于排查，后续按测试资源清理流程处理。

**剩余问题。** 验收对象是持久 JSON 导出快照，不是文件下载或浏览器端 PDF 生成。尚需 DEAD 运维与告警、消费失败恢复、历史等待任务补偿、真实故障演练、可重复初始化与测试资源自动回收。测试源代码仍有按需 DDL，后续应纳入统一迁移管理。

**企业场景与学习。** 新机制上线时必须同步更新旧回归路径；集成环境隔离包括数据库、缓存和消息通道。部署验收应核对中间状态及业务结果，不能只看 HTTP 200 或消息 SENT。

| 6 | 上线运行与容量边界 | 微信身份、指标告警、发布回滚与备份恢复；限流背压 | 故障发现时间、恢复过程、压测硬件/数据/并发模型和瓶颈；不只列 QPS |

智能规划保持轻量：意图路由 → 结构化规划草稿 → Java 校验约束 → 用户采纳与版本化保存。不得让模型直接绕过权限和事务修改账本。微服务、ES 等技术需有实际场景后再引入。

## 每阶段固定记录模板

后续每个有意义的交付追加一节，阶段未验收也要留下状态，不能等结束才补写结果。

```markdown
## E编号 · 阶段主题
- 日期 / 提交 / 负责人：
- 状态：调研 / 开发 / 测试通过 / 本地部署 / 验收完成（分别说明）
- 当时基线：已经有什么；缺少什么；运行版本与源码是否一致。
- 场景与问题：谁在什么操作下遇到什么；属于实际复现、测试发现还是风险推演。
- 动机与目标：不处理的后果；本阶段明确验收条件。
- 方案与取舍：选用机制、替代方案、复杂度与成本、正确性边界。
- 实现：业务规则、事务/并发、数据库、中间件、接口、迁移与回滚。
- 验证：环境、版本、数据量、故障注入、命令/报告链接、通过和失败范围。
- 实际效果：正确性结果；有测量才写性能数字；与预期收益分开。
- 剩余风险：未覆盖场景、依赖项、监控告警、人工恢复入口。
- 企业场景深化：这次学到的原理；上线如何发现与处理同类问题。
- 面试表达：场景 → 任务 → 行动 → 已有证据支持的结果；可追问的问题。
- 下一步：最优先工作与其验收门槛。
```

## 持续维护约定

1. 开发前先记录基线、问题分类和验收标准；开发中保留失败用例与方案变化的理由。
2. 开发后补齐提交、验证范围和剩余风险，同时更新交接文档的当前快照。代码完成、测试通过和部署验收分别记录。
3. 持久保留可复现的脚本、测试和脱敏报告；临时目录日志只辅助排查，不作为唯一证据。不得记录密钥、令牌或真实凭据正文。
4. 中断前写清未提交文件、最近一次通过的检查、未跑检查和下一条行动，降低恢复成本。
5. 简历可压缩成 4 条，但本记录不省略事实边界；预期收益不改写成已测数据。每条项目亮点都能追溯到阶段、代码与验收。
6. DDD 是业务建模与边界组织方法，TDD 是先失败测试再实现的开发循环。只对确实经历该循环的部分记录 TDD，不将「有测试」等同于全项目 TDD。
