# 后端成熟度评估与 DDD / TDD

评估日期：2026-09-20。基于当前仓库代码与已有本地验证，不代表生产认证、完整安全审计或性能压测结论。

## 结论

当前是具备工程化基础、可以联调的项目 MVP。账本比旅行模块成熟；尚不能宣称“企业级生产系统”或“已支持高并发”。Spring Boot、Redis、RabbitMQ 和 DDD 都是手段，生产成熟度取决于故障下的数据正确性、可观测性、可运维性及验证证据。

## DDD 与 TDD

- DDD（Domain-Driven Design，领域驱动设计）：围绕业务语言、边界和规则建模。例如账本和旅行独立上下文，Trip 是聚合，时间重叠和锁定限制是领域规则。当前采取 DDD 方向的模块化单体，不需要为了 DDD 拆微服务。
- TDD（Test-Driven Development，测试驱动开发）：先写表达预期行为的失败测试，再实现最小代码使其通过，最后重构。它是开发过程，不是架构，也不等于测试覆盖率。
- 两者正交。项目之前有自动测试，但没有证据表明整个项目按 TDD 建设。本轮前端排序纯函数先创建测试（缺少实现时失败），再实现并通过，可作为小范围 TDD 实例。服务端仍是最终规则与权限边界。

## 可验证的下一阶段

1. 可靠导出：数据库事务内写 Outbox，发布确认、重试、死信、补偿。验证“提交后进程退出”“重复投递”最终都只形成一个有效结果。
2. 并发正确性：固定租期失效和 Redis 中断实验；数据库幂等约束、版本校验与事务兜底；明确成功响应重放策略。
3. 生产基础：真实微信身份、数据库版本迁移、文件存储、结构化日志、指标与告警、备份恢复。
4. 压测：固定机器与数据量，覆盖账单写入、行程更新、地图缓存命中/未命中、导出积压，报告吞吐、P95/P99、错误率及数据库等待。未测量前不写“性能提升 X%”。

已有验证：上轮 Java 39 项和金额计算 4 项通过；高德真实查询成功且步行路线返回 56 个坐标点。本轮 UI 排序新增 4 项测试。数量说明回归范围，不代表完整正确性证明。
